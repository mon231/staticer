# frida-gadget 17.25.2 real TLS shape (PE + ELF)

Investigation for Task 1 of the TLS-support plan. Both binaries are the
real, genuine release assets fetched via `tests/conftest.py`'s
`fetch_frida_gadget()` (never synthesized):

- `frida-gadget-17.25.2-windows-x86_64.dll` (34,566,144 bytes)
- `frida-gadget-17.25.2-linux-x86_64.so` (37,065,128 bytes)

Inspection script (not shipped code, kept alongside this plan for
reproducibility): `.superpowers/sdd/2026-11-04-tls-support/_inspect_tls.py`.
Run with `python .superpowers/sdd/2026-11-04-tls-support/_inspect_tls.py`
from the repo root.

## Question 1: PE -- does `IMAGE_TLS_DIRECTORY.AddressOfCallBacks` have a non-null callback array?

**Yes.** The gadget DLL (x64) has a populated TLS directory:

- `DATA_DIRECTORY[IMAGE_DIRECTORY_ENTRY_TLS]`: VirtualAddress=`0x1f75e00`, Size=`40` (one `IMAGE_TLS_DIRECTORY64`, as expected).
- `StartAddressOfRawData` = `0x181f77810`, `EndAddressOfRawData` = `0x181f77a30`
- `AddressOfIndex` = `0x182016af0`
- `AddressOfCallBacks` = `0x1819abd70` (**non-null**)
- `SizeOfZeroFill` = `0`, `Characteristics` = `0x500000`

Walking the null-terminated callback pointer array at that VA yields
**3 non-null callback entries**:

```
callback[0] = 0x18191ee00
callback[1] = 0x1802aea44
callback[2] = 0x18191ef20
```

(All three are plausible in-image VAs, consistent with the gadget's own
image base of `0x180000000`.)

**Implication for Task 3:** the PE embedder cannot treat the TLS directory
as callback-free. It must handle `AddressOfCallBacks` pointing at a real,
non-empty callback array (3 entries in this exact release) -- i.e. it
needs to relocate/rebase both the TLS data block *and* the callback
pointer array (and the pointers within it) when the gadget is relinked at
a different base/address, not just copy a flat TLS data template.

## Question 2: ELF -- does `.rela.dyn`/`.rela.plt` contain TLSGD/TLSLD (call-site, needs relaxation), or only DTPMOD64/DTPOFF64/TPOFF64 (GOT-slot data patches)?

**Only GOT-slot data-patch relocations -- no TLSGD/TLSLD present.**

Full relocation-type histogram for the real `.so`:

`.rela.dyn` (76,621 relocations total):
| type | name | count |
|---|---|---|
| 1 | R_X86_64_64 | 335 |
| 6 | R_X86_64_GLOB_DAT | 33 |
| 8 | R_X86_64_RELATIVE | 76,239 |
| 16 | R_X86_64_DTPMOD64 | 14 |

`.rela.plt` (301 relocations total):
| type | name | count |
|---|---|---|
| 7 | R_X86_64_JUMP_SLOT | 301 |

Specifically:
- **Type 19 (`R_X86_64_TLSGD`): 0 occurrences.**
- **Type 20 (`R_X86_64_TLSLD`): 0 occurrences.**
- Type 16 (`R_X86_64_DTPMOD64`): **14 occurrences** -- present.
- Type 17 (`R_X86_64_DTPOFF64`): 0 occurrences.
- Type 18 (`R_X86_64_TPOFF64`): 0 occurrences.

So the gadget's TLS access model, as actually linked in this release, is
pure dynamic/data-patch (module-id slots filled by the dynamic linker at
load time via `DTPMOD64`); there are no call-site General/Local-Dynamic
TLS relocations (`TLSGD`/`TLSLD`) anywhere in `.rela.dyn` or `.rela.plt`.

**Implication for Task 3:** the ELF side is a **pure data-patch task** --
only GOT/TLS-slot values need to be rewritten (the 14 `DTPMOD64` entries,
plus whatever static TLS-block layout they index into). No code
relaxation (rewriting `call __tls_get_addr` sequences generated by
TLSGD/TLSLD) is needed for this real binary. Task 3's ELF scope can be
limited to GOT-slot/module-id patching; it does **not** need a TLS
code-relaxation sub-task for this gadget.

## Caveats / scope of this finding

- These findings describe this exact pinned release
  (`FRIDA_GADGET_VERSION = "17.25.2"` in `tests/conftest.py`) on
  linux-x86_64 and windows-x86_64 only. A different frida-gadget version,
  or a different architecture (e.g. x86-32, ARM64), could in principle be
  built/linked differently (e.g. with `-ftls-model=global-dynamic`
  producing TLSGD/TLSLD) -- this was not checked here and would need
  re-verification if/when the project supports those targets.
- No attempt was made to interpret *which* TLS variables the 14
  `DTPMOD64` slots/the 3 PE callbacks correspond to inside frida-gadget's
  own source -- that's out of scope for this investigation (Task 1 only
  answers the two gating questions above).
